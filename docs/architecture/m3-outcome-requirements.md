# M3 — Outcome Requirements and Next Best Question

An Outcome Requirement is an operator-declared relevance gate for one Opportunity: a stated outcome or piece of knowledge that matters now, later, or as context. It does **not** assert that the outcome is true. Its optional `conditionId` links a real Commercial Condition, which owns the proposition, explicit assumed/hypothesis intent, and assessed Evidence. An account-level Condition may therefore have different roles in different Opportunities. An unlinked Requirement derives `unknown`; an unrelated Condition creates no Requirement or question. Nothing in this relation describes ordering, causal prerequisites, buyer progress, or a Dependency graph.

The canonical record has a stable ID; owner, account and Opportunity anchors; immutable expected outcome and optional operator-authored question; mutable role and optional Condition link; active/retired lifecycle; source metadata and creation/update instants. Scope and sample boundaries are checked in the command and in the SQL trigger. The UI creates a Requirement without an answer in one step. Later, “Record answer” creates an actual Condition with explicit intent, optionally assesses an existing Evidence record, then links it. A typed answer without supporting Evidence remains assumed or a hypothesis. A supported linked Condition resolves the Requirement; contradiction conflicts it; assumed/hypothesis/unknown remain unresolved. Retirement removes a Requirement from question derivation without erasing it. A retired/missing/out-of-scope linked Condition yields unknown on read, never a phantom answer.

Within one Opportunity, Next Best Question chooses among active unresolved Requirements in this lexicographic order: `required_now` before `required_later` before `context`; within a role, `contradicted` before `unknown` before `assumed` before `hypothesis`; then original creation instant and stable ID. Conflict goes first because the current plan may rely on mutually incompatible evidence. Unknown precedes declared assumptions and hypotheses because there is no answer to examine yet. The latter remain explicit and still askable. Supported Requirements remain visible as resolved and generate no question. This order has no score and invents no authority, deadline or evidence age. An operator-authored question is used verbatim; otherwise the safe fallback is `Confirm whether: [expected outcome]`.

Today receives at most one question recommendation per open, qualified Opportunity, and only from an active `required_now` unresolved Requirement. It enters `evaluateCommercialPolicies` and the existing `rankRecommendations` portfolio order. The existing Today display limit bounds how many can appear. Its shape is `soon / unblocks / partial`, so actual overdue commitments and money warnings retain precedence; no unrelated Delta or timing observation raises its urgency. Recommendation carries Requirement ID, Condition ID when present, current Evidence IDs, state, role, reason, question, calculation time and Opportunity route. “Resolve this question” is navigation, not a claim to know whom or how to ask. No question is persisted or recalculation event emitted.

MEDDIC qualification remains its existing methodology projection. It neither creates Requirements nor supplies epistemic truth. This avoids two allegedly canonical answers to the same missing buyer question. Review sees the same ranked policy list; Search and Capture do not infer or silently close Requirements. Lead records keep the same Opportunity ID on qualification; the full editor appears only after qualification. No stage gate or automatic stage move is introduced.

Durability follows the [M1.1 checklist](m11-data-durability.md): browser-first guarded write, asynchronous cloud retry on load, state before audit event with a visible degraded-history warning, strict codec, sample exclusion from cloud and live restore, export manifest entry, format-5 restore preflight, parent/Condition scope validation, and dependency-order cloud merge (Accounts, Opportunities, Conditions, Requirements). Older backup versions remain readable; newer versions are refused. SQL uses owner-scoped composite foreign keys, an invoker scope trigger, RLS, authenticated-only read/write, no physical delete privilege, and Opportunity/Condition indexes. The migration is source code until explicitly applied and verified in the target Supabase project.

M4 may add ordering edges between these stable Requirement identities. It must not reinterpret `role` as an edge, materialize `unknown` as a fake Condition, or treat Next Best Question as an Intervention or Decision. The M3 model supplies relevance and current resolution only.
