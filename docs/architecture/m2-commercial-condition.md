# M2 — Commercial Condition

Starting point: `2c35ba357ce8fbe341484065643b810e8f468929` (clean; no later commit at intake). This ADR implements the first canonical Commercial State entity in `src/domain/commercialKernel/`. It is additive; it does not backfill a single proposition from Opportunity stage, MEDDIC, forecast labels, Capture text or historical data.

## Definition and boundaries

A **Commercial Condition** is a concrete proposition about a customer or commercial opportunity that the operator is currently working with and whose evidence status matters. “QA accepts six-month remaining shelf life” qualifies. “Call QA Friday” is an Action/Commitment. “The deal looks good” is too vague to assess. One Condition is one proposition; changing its subject or meaning requires retiring it and recording a new ID.

An **Event** records that something happened, including when Memoire recorded a Condition or linked Evidence. An **Evidence** record holds an observation and its original sentence, source and observed date. A **Condition** holds the proposition, operator intent, scope and stable Evidence references. Its link records say whether each Evidence item supports or contradicts that particular proposition. Evidence direction does not globally assign truth to every Condition. Event payloads contain identifiers and minimal from/to data, not copied propositions or evidence text.

The canonical terms are `supported`, `assumed`, `hypothesis`, `contradicted` and the derived absence `unknown`; there is no separate `fact` state and no numeric confidence. The model persists only `assumed` or `hypothesis` as operator intent. An active supporting link derives `supported`; any active conflicting link derives `contradicted` while retaining both sides. When no current linked evidence remains, the reading returns to intent. `unknown` means there is no relevant recorded Condition/answer; it is not a row created to fill a checklist. A missing referenced Evidence item is shown as unavailable and excluded from the reading, rather than treated as support.

## Identity, scope and time

Fields: stable `id`, `userId`, required canonical `accountId`, optional canonical `opportunityId`, concrete `statement`, small industry-neutral `conditionCategory` (`commercial`, `technical`, `financial`, `decision`, `delivery`, `other`), operator `intent`, separate `lifecycle` (`active`/`retired`), optional `validFrom`, `createdAt`, `updatedAt`, `SourceMetadata`, optional `isSample`, and bounded `evidenceLinks`. The category helps browsing; it does not drive a methodology score. `validFrom` is supplied only when the business-effective date is known. System creation and update timestamps are recorded independently. Evidence retains its own `observedAt` and `recordedAt`; M2 does not reconstruct an as-of state.

An Account-level Condition has no Opportunity ID and may use only account-level Evidence with that canonical account ID. An Opportunity Condition is tied to the same canonical Account ID; it can use account-level Evidence or Evidence on the same Opportunity. Legacy Capture Evidence with an empty account ID can be explicitly attached only when its canonical Opportunity ID matches. Names never establish a link. Conditions do not have a Thread ID in M2: existing Threads organize commercial work, while the proposition's smallest unambiguous scope is Account or Opportunity. An early Lead may have a Condition in the kernel, since qualification keeps the same Opportunity ID; the Leads surface does not expose the full Condition editor, and the qualified Opportunity drawer does.

## Evidence assessment and supersession

`evidenceLinks` is a bounded append-only list on the Condition row. Each entry has `evidenceId`, `assessment` (`supports`/`contradicts`), and a system `recordedAt`. An optional `supersedesEvidenceId` explicitly replaces one earlier link for this Condition. This is a relation assessment, not a second Evidence text store or a general graph. One Evidence ID may be assessed against multiple Conditions; a Condition can cite many Evidence IDs. The single-row aggregate makes condition creation and link addition locally atomic. Database constraints check ownership, scope, duplicate IDs and replacement order. Later assessments cannot silently rewrite old links.

The legacy technical Evidence summary uses the latest observation per broad scope/category. That rule is retained for its existing Delta use, but it cannot decide a Condition conflict between independent sources. Condition evaluation recognizes source revisions only when both a stable `sourceId` and explicit `sourceUpdatedAt` exist; it uses the existing observed/recorded order within that lineage. Otherwise observations remain independent until an operator explicitly marks replacement. If a newer unassessed source revision displaces an older linked item, the old item remains in history and does not automatically lend its assessment to the new item. A later Finance observation does not win over an earlier commercial contact simply by being newer. The operator can link both to obtain `contradicted`, or confirm a replacement when the source genuinely supersedes an earlier observation.

Example: one contact says budget approved and Finance says still pending. Link the former as `supports` and the latter as `contradicts`; the Condition reads `contradicted` and shows both sentences, dates and sources. If a signed approval explicitly replaces the pending Finance statement, link it as `supports` with `supersedesEvidenceId` pointing to the older Finance Evidence ID. The old row and link remain accessible as history.

## Persistence and security

`commercial_conditions` is a relational Kernel table with named columns, a bounded JSONB reference-assessment list, owner/account/opportunity indexes, ownership RLS, authenticated-only grants and composite owner/anchor foreign keys. The database verifies linked Evidence IDs through an invoker function under Evidence RLS; it rejects cross-tenant and wrong-scope links. The Opportunity account match is checked when a canonical `opportunities.account_id` exists. SQL prevents proposition/scope rewriting, link deletion or rewriting, and revival after retirement. There is no client-only trust boundary.

The table has a real `KernelCodec`, durable local writes, background account sync with visible failure status, owner filtering, and sample isolation. A refused local write returns failure before any event or success UI. Once state is saved, an event failure returns accepted with a warning, so the operator does not retry and duplicate the state. The same Condition ID is used on repeated cloud sync/restore. Browser-local acceptance alone is never described as confirmed account durability. Physical deletion and cross-device conflict behavior retain the M1.1 limitations.

Backup format **4** registers the Condition codec after Account, Opportunity and Evidence dependencies in `canonicalContracts`; export pages the new table and includes it in the manifest. Restore validates every Condition and its referenced anchors before mutation, then writes the local replacement with a rollback journal and merges cloud rows in registry order. Older formats remain readable; older app versions reject format 4. Samples are removed from live restore and never sent to cloud. A malformed or foreign reference rejects the entire restore before local mutation. Cloud partial failure is reported per collection; the user keeps the backup.

Evaluation builds Evidence and supersession indexes once and reads each link once. A test projects 2,400 Conditions across 300 Opportunities and 7,200 Evidence items. The Opportunity drawer computes the projection once for its visible scope; it does not issue a network request per Condition. Database indexes cover owner/account and owner/Opportunity lookups.

## Product and follow-on boundaries

The qualified Opportunity drawer has one compact “Commercial state” section. It starts with an honest empty state and “Add condition.” The operator selects a canonical Account, writes a proposition, chooses assumption or hypothesis as fallback, and may select existing Evidence plus a supporting/conflicting assessment. Category and business-effective date are progressive details. Each reading shows the statement, state, source sentence, observed/recorded dates, unavailable links, and retained replaced evidence. Users can change intent, add an assessed Evidence link, or retire a proposition. Statement and scope cannot be overwritten in place.

Existing MEDDIC remains a methodology projection with its own evidence gaps and score; Conditions do not copy its fields or replace its current calculation. A later mapping can consume the canonical propositions and Evidence links. Capture continues to propose Evidence, not Conditions; there is no silent Condition creation. Search remains the existing deterministic engine, with no parallel Condition search. Today receives no new Condition priority rule: materiality and required outcomes need a later explicit model. No new navigation, dashboard, AI inference, dependency graph, Time Machine or M3 feature is introduced.

## Known debt and M3 gate

- **BLOCKS M3 if unmet:** M2 final SHA must pass the full required suite; Condition and Evidence migration must be applied and verified on the intended environment before promising live cloud use. No production schema or historical data is mutated by this repository change alone.
- **FIX SOON:** legacy Opportunity and Capture records can lack canonical Account IDs. The user must select an actual Account to create a Condition. Wider canonical account-link reconciliation belongs in its own work and must not infer historical truth. The existing physical-delete/cloud retry and cross-device conflict limitations remain from M1.1.
- **SAFE TO DEFER:** direct account-level creation UI, general nontechnical Evidence authoring, Conditions in Search/Today, MEDDIC mapping, and explicit business-valid end dates. M2's first product path is the Opportunity drawer; the kernel supports account-level and Lead-linked records without manufacturing them.
