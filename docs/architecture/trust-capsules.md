# Trust capsules

M25 wraps an M24 minimal statement in a bounded, exact-field `memoire.trust-capsule` version 1 artifact. It carries the statement's UUID, declared party scope, public promise reference and source/issuance times, a SHA-256 digest, and an optional ECDSA P-256/SHA-256 signature. The exchanged shape adds no private canonical IDs, account context, money values, access tokens or private keys. Unknown fields and algorithms are refused. Normalization fixes field order before UTF-8 JSON serialization; digest/signature identity is defined over this normalized v1 representation, not arbitrary JSON byte formatting.

Integrity hashes the normalized `{format,version,statement}` core. A signature signs that same core plus the integrity object. Public keys use standard base64 SPKI; signatures use the Web Crypto 64-byte P1363 representation. Optional host-provided CryptoKeys remain under host custody; the module exports only a public key and signature, never a private key. A supplied pair is checked before the signed capsule is returned. See the [Web Crypto signing reference](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/sign) for the ECDSA encoding and algorithm contract.

`verifyTrustCapsule` separately returns integrity validity, optional signature validity, the public-key fingerprint and whether it matches an independently configured issuer key fingerprint. An expected fingerprint makes an unsigned or mismatched-key capsule fail closed. A capsule-provided public key alone does not establish organizational identity. Even a valid, agreed key proves a statement was signed by that key; independent commercial and organizational verification remains the recipient's responsibility. `issuerOrganizationIdentityVerified` and `acceptedCommercialTruth` remain false.

Review extends the existing External promise statements panel. Owners can download an unsigned integrity capsule from an already issued statement. Recipient users check JSON and their agreed party reference, optionally provide a fingerprint agreed through another channel, inspect the result and explicitly confirm receipt. No signing key is generated or persisted by the product UI. The host-level module supports signing for deployments that already manage key custody; certificate services, organizational identity, private-key storage, key rotation/revocation directories and legal-signature claims are outside this phase.

Receipt reuses the existing immutable M17 source Event and preserves the complete checked capsule in its raw payload. Source identity includes a bounded hash of the complete issuer reference, statement UUID and normalized full-capsule fingerprint. The same bounded issuer namespace repair also covers plain M24 statement intake; the full declared reference remains in the retained payload. The exact capsule retries idempotently; a separately signed representation is a distinct attributed source receipt. It does not implicitly supersede or promote another claim. Real receipts retain owner RLS, current backup/export and no canonical subject links. Sample mismatch is denied; samples remain partitioned. Issuer times remain reported content, while Event occurrence uses local receipt time, preventing claimed future knowledge from becoming historical canonical state.

No new canonical entity, migration, history source, backup format, credential store, cross-company permission or primary navigation is introduced. Only existing durable observation Events persist after confirmation. Capsule checks are derived and can be repeated after export/restore. A digest is transport integrity and can be recomputed by an attacker; consumers needing issuer authenticity must require their independently agreed key. The interface makes this distinction explicit. Production remains pending P1.
