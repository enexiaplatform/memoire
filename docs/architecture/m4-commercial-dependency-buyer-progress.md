# M4 — Commercial Dependency and Buyer Progress

M4 starts from M3 Outcome Requirements at commit `edf0d598ea9f6134ed3156899d3a945857ef06c9`. A Requirement says what must be known or achieved for an Opportunity. A linked Condition says what is believed and which Evidence supports or contradicts it. A Dependency says only that one Requirement cannot be resolved before another. The only persisted edge is `dependent Outcome Requirement requires prerequisite Outcome Requirement`, within one owner and Opportunity, with a human explanation. The operator confirms it. No order is inferred from timestamps, sequence, stage, role, activity, money, or text; no generic graph, Decision, Intervention, or probability entity is introduced.

The canonical `commercial_dependencies` record has stable ID, owner, Opportunity, dependent and prerequisite Requirement IDs, `basis`, active/retired lifecycle, manual source metadata, and creation/update instants. Identity and provenance are immutable after creation; retirement preserves the historical assertion. The command validates both active endpoints, workspace/sample scope, duplicate active pair, self-edge, and cycle before the guarded browser write. The database adds composite owner foreign keys, an active-pair unique index, a scope and cycle trigger serialized per owner/Opportunity, authenticated owner RLS and no DELETE grant. Active edges touching retired Requirements are ignored on read; the edge remains in history. Corrupt graphs suppress the derived blocker and question instead of guessing.

`deriveKnownBlockers` starts at active unresolved `required_now` Requirements and follows active hard prerequisites that are themselves unresolved. It returns the deduplicated unresolved leaves and one concise leaf-to-root explanation path per affected root. A resolved prerequisite no longer blocks. A root with no unresolved prerequisite is its own blocker. This is the smallest *known* set, not a claim that every real-world dependency has been entered. Paths retain Requirement and Dependency IDs and operator-authored reasons. The UI shows “Waiting For,” a small add/retire/why control, and the upstream Next Question. The policy emits at most one question per qualifying Opportunity through existing recommendation and ranking rules; Review inherits that list. There is no separate Today queue or graph editor.

Buyer Progress is a projection, never a stored score. It includes only canonical PO/payment receipt events, a Commitment explicitly owned by the customer when made or completed, or Evidence explicitly marked customer-provided that currently supports a resolved active Requirement. Legacy Evidence has `provided_by = NULL` and is not assumed to be customer-provided. The Opportunity panel can capture a new technical observation with an explicit provider; it becomes a buyer signal only after the operator links it into a supported Requirement. Seller activity is shown as a separate recorded count/date and does not increase buyer progress. A missing signal means only that none qualifies in the available records; it does not prove the customer did nothing.

M1.1 durability applies. The dependency codec is in the canonical registry, workspace loader, sample cleanup, cloud export manifest and format-6 backup/restore. Restore validates full endpoint scope and graph integrity before changing local data; cloud merge keeps stable IDs and orders Dependencies after Requirements. State is saved before a `dependency_created` or `dependency_retired` audit event. A failed history write reports accepted state with degraded history; a failed state write emits no event. Sample edges stay browser-only and are excluded from live restore. Evidence's optional provider travels through its existing codec and cloud column, without backfilling old records.

Local tests cover graph shape, cycles, scope, retirement, leaf derivation and explanation, policy selection, seller/buyer separation, legacy unknown providers, sample isolation, actual Postgres migration and RLS, codec/restore round trips, failed writes, and a 300-Opportunity/3,000-Requirement/3,000-Condition/3,000-Evidence/2,700-edge case. The SQL migration and M2/M3 predecessors must be verified in the target Supabase project before live use; source migration and local Postgres success do not establish target deployment.
