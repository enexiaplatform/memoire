# M7.1 — Historical integrity foundation

Starting source SHA: `d8caf55ec3298be0033367ab1a757c171ce9d7c3`. The intended M2–M5 and M7 target Supabase migrations were not verified as deployed. This migration is code and local database verification only.

## Contract and boundary

Current State is the latest canonical row. A State Revision is the accepted full source-state snapshot, with owner, entity identity, monotonically increasing revision number, mutation identity, operation, server/system `recordedAt`, and schema version. A Commercial Event records selected business meaning and can fail after an accepted state write; it is not the reconstruction source. A Decision Basis Snapshot freezes the explicit Decision's reasoning at finalization; it is not a general history of other mutable entities.

The coverage marker `historyGuaranteedFrom` is written exactly once for each owner. Initial activation records a baseline of current covered rows at activation time. Old `createdAt`, `observedAt`, `validFrom`, and other business dates stay inside the state; they do not move the baseline backward or fabricate intervening revisions. Reads before the marker return `pre_coverage`. Missing/corrupt sequence or unsupported schema returns an explicit gap. Cutoff reads select the latest recorded revision at or before the instant and never use a later revision merely because its business date was earlier.

The source manifest in `historicalIntegrity.ts` covers Opportunities, Conditions, Evidence, Outcome Requirements, Dependencies, Timing Assertions, and Commitments. Condition–Evidence links are embedded in Condition state. Opportunity snapshots retain all persisted fields except cosmetic `updatedAt`/`storageMode`, including stage, status, value, currency, expected close period, probability, forecast metadata, evidence category, recommendations, and account linkage. M7 Decisions remain immutable basis records with their own canonical retention; Commercial Events, derived readings, imports, documents, and UI projections are not state revisions.

Full snapshots were chosen because the covered records are bounded personal-commercial state and a reader can reconstruct a cutoff without replaying patches. The cost is linear history growth and local browser storage pressure. No source record's business-effective date is inferred from the system acceptance time. Revision order is per owner/entity; `mutationId` and unique revision sequence support idempotent cloud constraints. Local no-op writes do not append revisions.

## Atomicity

In the browser, the existing restore journal writes canonical collection, revisions, and coverage marker as one rollback unit. A refused write restores the previous bytes or leaves an interruption journal for recovery. Cloud trigger capture runs in the same PostgreSQL transaction as each covered row mutation. A rejected revision insert aborts that row mutation. The activation RPC installs a baseline under a per-owner transaction lock; an unavailable migration prevents the covered app cloud writer from claiming account durability. Cloud RLS exposes owner-scoped reads only and rejects direct history writes. Selective Commercial Event failures remain accepted-with-warning and cannot remove a required State Revision.

Sample history has a separate `sample` scope and is removed with the sample workspace. The cloud tables are included in paged export, and backup format 9 preserves revision and coverage records. A legacy browser backup establishes a new boundary at restore time, never at export time. Local historical backups retain their original boundary and sequence. The current cloud restore path merges table by table, so a signed-in backup carrying historical records is rejected before changing local state. Legacy covered account restore probes the history table without writing; if the migration exists it is also rejected before changing state, avoiding synthetic trigger revisions. On a target without the migration, the older merge path remains available but carries no cloud history guarantee. A transactional cloud history restore is an M8 blocker.

## Reconstruction readiness

Condition epistemics, Requirement resolution, next blocking question, known blockers, Commercial Time, and Forecast Defensibility have covered mutable canonical inputs, subject to a verified boundary and later cutoff composition. Buyer Progress is incomplete: purchase-order and payment signals still depend on selective Commercial Events, and its recorded-activity comparison needs a cutoff-safe source. The M8 implementation must either give those signals canonical revision-covered state or explicitly exclude their historical claims. M8 also needs a transactional, ownership-checked cloud history restore that imports current state, original revisions, and original boundary together; legacy cloud restore must establish its boundary without generating false intermediate changes.

The low-level local and cloud query APIs return a single entity revision at a system-time cutoff. They do not build a Time Machine view, join all source types, or recreate derived projections. No Time Machine UI is implemented here.

A synthetic browser benchmark on this development host committed 1,000 consecutive revisions of one Condition with a 1 KiB statement in 2.47 seconds total; the revision JSON reached 1,378,784 bytes. A 100-revision tiny-row run took 19 ms and used 35,983 bytes. These are local in-memory-storage measurements, not browser quota, target-cloud latency, or representative customer data. The journal duplicates the history value transiently during each write, so a browser quota can be reached earlier than the final JSON size suggests. This needs a bounded real-browser workload before M8.

## Verification and limits

PGlite tests exercise baseline activation, no-op retry, accepted update, business/system time separation, and cross-owner/anonymous RLS. Browser tests exercise atomic rollback, cutoff, gap statuses, sample cleanup, and legacy restore boundary. The static contract check links every historical source to its canonical codec, migration and export. Target Supabase migration application and live RLS have not been verified. Browser quota and historical growth require measured operating limits before M8. Existing cloud restore is still a merge with partial-failure semantics for legacy backups; it is not an atomic historical restore.
